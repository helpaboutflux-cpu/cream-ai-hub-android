01 — OVERVIEW

Soft Hub 개발자 포털 개요

Soft Hub는 Lemon soft가 만든 80여 종의 웹 도구가 모여 있는 무료 허브입니다. 그 옆에 발견(Discover) 탭이 있고, 이 탭은 다른 개발자가 만든 도구를 전시하는 자리입니다. 개발자 포털(portal.html)은 그 발견 탭에 도구를 올리고 관리하는 화면입니다.

무엇을 만들 수 있나

Soft Hub가 요구하는 것은 단 하나, 브라우저에서 열리는 웹 주소입니다. 정적 HTML 한 장이어도 좋고, GitHub Pages·Cloudflare Pages·Netlify 같은 무료 호스팅에 올린 사이트여도 좋습니다. 서버가 없어도, 데이터베이스가 없어도 됩니다. Soft Hub는 그 주소를 발견 탭 카드와 상세 페이지에 걸어 줄 뿐입니다.

가능 정적 웹 도구

계산기, 변환기, 타이머, 메모장, 퀴즈, 이미지 편집처럼 브라우저 안에서 끝나는 모든 것.

가능 이미 배포한 사이트

이미 공개된 주소가 있다면 그대로 등록합니다. Soft Hub가 복사하거나 호스팅하지 않습니다.

가능 LK 로그인이 필요한 도구

4장의 LK 로그인 API를 붙이면 사용자가 Soft Hub 계정으로 로그인할 수 있습니다.

불가 설치가 필요한 프로그램

exe·apk 설치 파일, 확장 프로그램 설치 링크는 도구 주소로 쓸 수 없습니다.

발견 탭에 도구가 노출되는 방식

발견 탭은 community_apps 표에서 status = approved 인 행만 읽습니다. 승인 전(pending)이나 반려(rejected) 상태의 도구는 본인과 관리자에게만 보이고 방문자에게는 보이지 않습니다.

  1. 분류별 섹션 — 도구는 6개 섹션(생산성·게임·디자인·교육·생활·기타) 중 하나에 들어갑니다. 섹션 번호는 01~06으로 고정입니다.
  2. 콤팩트 카드 — 카드는 아이콘 타일 + 이름 + 한 줄 소개 + 분류칩 + 제작자로 구성됩니다. 큰 썸네일은 쓰지 않습니다.
  3. 검색 — 이름, 소개, 제작자, 분류, 주소를 한 번에 훑습니다. 여러 낱말을 띄어 쓰면 모두 포함된 도구만 남습니다.
  4. 칩 필터 — 전체 · 저장한 도구 · 분류별 칩. 도구가 없는 분류의 칩은 숨겨집니다.
  5. 저장 별 — 카드 오른쪽 위 별을 누르면 이 기기에 저장되어 '저장한 도구' 칩에 모입니다.
  6. 카드 클릭 — 팝업 없이 tool.html?id=... 상세 페이지로 이동합니다.
상단의 슬림 배너(관리자가 관리), 카테고리 섹션, 검색, 칩, 저장 별은 모두 그대로 유지됩니다. 이번 개편은 카드의 생김새만 Soft Hub 본체의 도구 카드와 같아지도록 맞춘 것입니다.

Soft Hub의 디자인·운영 원칙

발견 탭과 상세 페이지는 Soft Hub 본체와 같은 규칙으로 그려집니다. 도구를 만들 때도 이 규칙을 지키면 훨씬 자연스럽게 어울립니다.

원칙내용이유
이모지 0건화면·안내 문구·버튼 어디에도 이모지를 쓰지 않습니다. 아이콘은 모두 SVG입니다.기기마다 다르게 그려지고, 문서·코드에서 깨지기 때문입니다.
팝업 0건alert()·confirm()·prompt()·모달을 쓰지 않습니다. 모두 인라인 배너와 인라인 확인으로 처리합니다.흐름이 끊기지 않고, 화면을 캡처하거나 공유해도 상태가 남습니다.
자체 UI 부품네이티브 <select> 대신 자체 드롭다운, 기기 색 선택기 대신 자체 색 피커를 씁니다.라이트·다크 어디서나 같은 모양을 유지하기 위해서입니다.
고딕만궁서·명조·세리프 폴백을 쓰지 않습니다. Pretendard 계열 고딕 스택만 사용합니다.플랫폼별 대체 글꼴로 화면이 흔들리는 것을 막습니다.
0원 정적 웹 친화서버·DB·결제 없이 동작하는 도구를 우선합니다. 저장은 브라우저(IndexedDB)나 사용자의 Google Drive를 씁니다.운영비가 들지 않아야 누구나 오래 쓸 수 있습니다.
라이트·다크 모두cream_theme 값에 따라 두 테마를 모두 지원하고, 390px 모바일에서 가로 스크롤이 없어야 합니다.휴대폰 사용자가 대부분이기 때문입니다.
도구 안에 이모지를 넣어도 등록이 반려되지는 않지만, 발견 탭 카드와 상세 페이지에는 이모지가 나오지 않습니다. 카드의 표정은 아이콘 + 브랜드 컬러가 담당합니다.
02 — PUBLISH

도구 등록부터 승인·게시까지 단계별 사용법

처음 한 번은 5분이면 끝납니다. 순서는 로그인 → 빌더 → 제출 → 승인 대기 → 게시이고, 중간에 막히는 지점마다 이 장에서 설명합니다.

1) LK ID 로그인과 대시보드 진입

  1. portal.html을 엽니다. 로그인하지 않아도 포털 메인은 열리지만, 빌더·통계·프로젝트는 로그인이 필요합니다.
  2. 상단 오른쪽의 로그인(또는 화면의 LK ID로 로그인)을 누르면 auth.html로 이동합니다.
  3. 이메일·비밀번호로 로그인하거나 Google 계정으로 계속을 누릅니다. 처음이라면 같은 화면에서 계정을 만들 수 있습니다.
  4. 로그인하면 portal.html로 되돌아오고, 상단에 내 닉네임이 보입니다.
  5. 포털 내비의 대시보드를 누르면 개요(내 도구 수·게시 중·승인 대기·반려)가 나옵니다. 대시보드 안의 하위 탭으로 도구 등록·수정, 통계, 프로젝트를 오갑니다.
로그인 세션은 이 브라우저에 저장됩니다. 다른 탭에서 로그아웃하면 포털도 곧바로 로그아웃 상태로 바뀝니다. 세션이 만료되면 등록·수정 시 로그인이 만료되었습니다 안내가 인라인으로 뜹니다.

고민되면 사용자가 이 도구를 언제 여는지를 기준으로 고르세요. 아침에 여는 돈·일정 도구는 생활, 작업 중에 여는 문서·코드 도구는 생산성·개발입니다.

색은 하나만 정합니다. 나머지(밝은 배경, 테두리, 다크 모드에서의 색)는 Soft Hub가 color-mix로 자동 계산하므로 어떤 색을 골라도 카드가 깨지지 않습니다. 다만 너무 밝은 색(#fef08a 같은)은 흰 배경에서 아이콘이 흐려 보이니, 중간 밝기 이상의 채도 있는 색을 권합니다. 추천 색 9종이 색상 줄 옆에 있습니다.

4) 스크린샷 등록 가이드

스크린샷은 선택이지만, 있으면 상세 페이지의 인상이 크게 달라집니다. 두 가지 방법이 있습니다.

방법 A — 외부 이미지 URL 입력

  1. 이미지를 어딘가에 올리고 직접 열리는 이미지 주소를 복사합니다. 주소가 .png·.jpg·.webp로 끝나거나, 열었을 때 이미지만 보이면 됩니다.
  2. 빌더의 스크린샷 칸에 붙여넣습니다.
  3. 여러 장은 쉼표(,)로 이어 적습니다. 줄바꿈·세미콜론도 같은 역할을 합니다.
여러 장 입력 예시 
https://cdn.example.com/tool-main.webp, https://cdn.example.com/tool-light.webp, https://cdn.example.com/tool-dark.webp
  • 최대 8장까지 갤러리에 들어갑니다. 첫 장이 대표 이미지입니다.
  • 같은 주소를 두 번 넣으면 한 번만 들어갑니다. http(s)가 아닌 주소는 무시됩니다.
  • 도구 페이지에서 이미지를 불러오지 못하면 아이콘으로 자동 대체됩니다(깨진 이미지가 남지 않습니다).
  • 권장 비율은 16:10이고, 가로 1200px 정도면 충분합니다.

방법 B — Cloudinary WebP 압축 업로드

관리자가 Cloudinary를 연결해 두면 빌더의 이미지 업로드 탭이 켜집니다. 파일을 고르면 브라우저가 긴 변 1200px, WebP 품질 0.82로 줄여 올리고, 돌아온 주소를 자동으로 채웁니다.

  1. 스크린샷 입력 방식을 이미지 업로드로 바꿉니다.
  2. 이미지를 끌어다 놓거나 눌러서 고릅니다(PNG·JPG·WebP, 12MB 이하).
  3. 압축·업로드가 끝나면 미리보기와 함께 "업로드 완료 · 1200x750 WebP · 84 KB"처럼 결과가 표시됩니다.
  4. 마음에 들지 않으면 [비우기]로 지우고 다시 고릅니다.
업로드 탭이 비활성 안내로 보이면 Cloudinary가 아직 연결되지 않은 것입니다. 그때는 방법 A(이미지 URL)를 쓰거나 스크린샷을 비워 두세요. 등록 자체에는 영향이 없습니다.

5) Web Launcher 프로젝트 불러오기

이미 Web Launcher(launcher.html)로 사이트를 배포했다면 주소를 다시 타이핑할 필요가 없습니다. 도구 주소 칸 오른쪽의 불러오기를 누르면 이 기기에 저장된 Launcher 프로젝트 목록이 열립니다.

  • 목록에서 하나를 고르면 주소가 채워지고, 이름 칸이 비어 있으면 도구 이름도 함께 채워집니다.
  • 목록이 비어 있다면 이 브라우저에 Launcher 프로젝트가 없다는 뜻입니다(다른 기기에서 만든 것은 보이지 않습니다).
  • 불러온 주소도 등록 전에 https:// 형식인지 자동으로 검사합니다.

프로젝트 인라인 삭제

04 — LK LOGIN API

LK 계정 로그인 API 연동 완전 가이드

외부 도구에 LK 계정으로 로그인 버튼을 붙이면, 사용자는 Soft Hub가 직접 만든 로그인·동의 화면을 거쳐 자신의 프로필(고유 ID·닉네임·프로필 색상)만 넘겨 줍니다. 비밀번호는 절대 전달되지 않습니다.

1) 개념 — OAuth 2.0 스타일 흐름

01
도구가 로그인을 요청합니다

사용자가 내 도구의 [LK 계정으로 로그인]을 누르면 oauth.html로 이동합니다. 이때 client_id, redirect_uri, state, scope를 함께 보냅니다.

02
Soft Hub가 요청을 검증합니다

oauth.html이 Client ID가 등록된 앱인지, Redirect URL이 허용 목록과 정확히 같은지 확인합니다. 다르면 이동하지 않고 안전한 오류 화면을 보여 줍니다.

03
사용자가 로그인하고 동의합니다

로그인하지 않았으면 LK ID 로그인 화면이, 로그인했으면 동의 화면이 나옵니다. "이 도구에 내 LK 계정 정보를 전달할까요?"에서 [동의하고 계속]을 누릅니다.

04
일회용 code를 들고 돌아옵니다

redirect_uri?code=...&state=...로 돌아옵니다. code는 5분 동안 한 번만 쓸 수 있습니다.

05
code를 프로필로 교환합니다

내 콜백이 code·client_id·redirect_uri를 oauth_exchange_code에 보내면 고유 ID·닉네임·색상이 돌아오고, code는 즉시 만료됩니다.

2) 사전 준비 — 앱 만들기

  1. 포털 내비의 API 대시보드(portal.html#api)로 갑니다. 로그인하지 않았으면 LK ID 로그인을 먼저 합니다.
  2. 새 앱 만들기를 누르고 앱 이름을 적습니다. 동의 화면에 이 이름이 그대로 나오므로 사용자가 알아볼 수 있는 이름이어야 합니다.
  3. 허용 Redirect URL을 한 줄에 하나씩 넣습니다. 최대 10개입니다.
  4. [앱 만들기]를 누르면 Client ID가 자동 발급됩니다. lkc_로 시작하는 28자입니다.
  5. 목록에서 복사로 Client ID를 가져가고, 필요하면 연동 코드를 눌러 바로 쓸 코드를 복사합니다.

앱을 만들면 공개 승인 대기 상태입니다. 만든 본인은 바로 테스트할 수 있지만, 다른 사용자에게 열려면 관리자 공개 승인이 필요합니다(06-2). 사용자는 auth.html → 연결된 앱에서 언제든 권한을 해제할 수 있습니다.

3) Step 1 — 로그인 요청 URL 만들기

사용자를 아래 주소로 보냅니다. state는 매번 새로 만드는 임의 문자열입니다.

요청 주소 형식 
https://helpaboutflux-cpu.github.io/cream-ai-hub-android/oauth.html
  ?client_id=lkc_xxxxxxxxxxxxxxxxxxxxxxxx
  &redirect_uri=https%3A%2F%2Fstudio-pine.example%2Fcallback
  &response_type=code
  &scope=profile%3Abasic
  &state=f3k9q2m7x1
파라미터필수값설명
client_id필수내 Client IDAPI 대시보드에서 발급받은 값. 없으면 오류 화면.
redirect_uri필수등록한 주소승인 결과를 받을 주소. 반드시 URL 인코딩합니다.
response_type필수code지금은 code 방식만 지원합니다.
scope권장profile:basic생략하면 profile:basic으로 처리합니다.
state필수임의 문자열 8~64자돌아왔을 때 내가 보낸 요청이 맞는지 확인하는 값(CSRF 방지).

4) Step 2 — 사용자가 보는 로그인·동의 화면

oauth.html은 요청을 받으면 아래 순서로 동작합니다. 이 화면은 Soft Hub가 직접 운영하며, 내 도구가 흉내 낼 필요가 없습니다.

  1. 앱 확인 — Client ID로 앱 이름과 허용 주소를 읽습니다. 없거나 중지된 앱이면 오류 화면.
  2. 주소 확인 — redirect_uri가 허용 목록과 정확히 같지 않으면 이동하지 않고 오류 화면에서 멈춥니다.
  3. 로그인 — 로그인 상태가 아니면 LK ID 로그인(이메일·비밀번호 또는 Google)을 인라인으로 보여 줍니다.
  4. 동의 — 로그인 상태면 "OO에 내 LK 계정 정보를 전달할까요?"와 함께 전달될 항목, 돌아갈 주소를 보여 줍니다.
  5. 발급 — [동의하고 계속]을 누르면 일회용 code를 만들어 redirect_uri?code=...&state=...로 이동합니다.
  6. 취소 — [취소]를 누르면 아무 정보도 넘기지 않고, 사용자가 직접 [서비스로 돌아가기]를 누를 때 error=access_denied&state=...로 돌아갑니다.
화면 오른쪽 아래에는 이 서비스 신고 버튼이 항상 떠 있습니다. 사용자가 내 도구를 의심하면 그 자리에서 신고할 수 있고, 신고는 관리자만 봅니다(6장 참고).

5) Step 3 — 콜백에서 state 검증 후 code 교환

콜백 페이지에서는 세 가지를 반드시 합니다.

  1. 오류 먼저 확인 — error가 있으면 사용자가 취소한 것이므로 로그인 실패로 처리합니다.
  2. state 비교 — 로그인을 시작할 때 저장한 값과 다르면 code를 쓰지 않습니다.
  3. code 교환 — oauth_exchange_code에 p_code, p_client_id, p_redirect_uri를 보냅니다.

7) 보안 체크리스트

  • state를 매번 새로 만들고 비교한다 — 다른 사이트가 사용자를 몰래 로그인시키는 공격(CSRF)을 막습니다.
  • Redirect URL은 정확히 일치해야 통과한다 — 등록한 주소와 한 글자라도 다르면 oauth.html이 이동을 거부합니다.
  • code는 1회용, 5분 만료 — 교환에 성공하면 즉시 used 처리됩니다. 같은 code를 저장하거나 재사용하지 마세요.
  • 비밀 키(secret)를 만들지 않는다 — 정적 웹앱은 비밀을 지킬 수 없습니다. 그래서 이 API는 secret을 쓰지 않고 code 교환을 client_id + redirect_uri로 묶습니다.
  • 민감 정보를 저장하지 않는다 — LK 로그인은 비밀번호를 주지 않습니다. 받은 값을 서버 없이 브라우저에만 저장하고, 남에게 보내지 마세요.
  • 받은 값을 그대로 HTML에 넣지 않는다 — 닉네임은 textContent로 넣어 스크립트 주입을 막습니다.
  • Client ID가 노출되어도 괜찮다 — Client ID는 공개 값입니다. 다만 유출이 의심되면 API 대시보드의 [재발급]으로 새 값으로 바꾸세요.
  • 앱 주소를 정직하게 적는다 — 동의 화면에는 등록한 앱 이름과 돌아갈 host가 그대로 보입니다. 사칭은 신고 대상입니다.

07 — FAQ

자주 묻는 질문과 문제 해결

Q등록했는데 발견 탭에 안 보입니다.

대시보드 → 프로젝트에서 상태를 확인하세요. 승인 대기면 아직 관리자가 확인하지 않은 것입니다. 반려됨이면 카드의 반려 사유를 읽고 고친 뒤 다시 제출하세요.

QRedirect URL이 맞는데 계속 "등록된 주소로만 돌아갈 수 있습니다"가 나옵니다.

다음을 순서대로 비교하세요. 1) 끝 슬래시(/callback vs /callback/), 2) www. 유무, 3) http와 https, 4) 포트 번호, 5) 쿼리 문자열. API 대시보드에서 주소를 복사해 붙이고, 코드에 적은 값도 같은 방식으로 복사하세요.

Q승인이 하루 넘게 안 됩니다.

관리자가 순서대로 확인합니다. 주소가 열리지 않거나, 소개와 실제 내용이 다르거나, 스크린샷이 깨져 있으면 확인이 늦어집니다. 그 상태로 다시 제출하면 대기열 뒤로 밀리니, 스스로 점검한 뒤 한 번만 제출하세요.

Q스크린샷이 상세 페이지에서 안 뜹니다.

주소를 브라우저 새 탭에 붙여 열어 보세요. 이미지가 바로 보이지 않으면 다른 사람에게도 보이지 않습니다. 로그인이 필요한 클라우드 링크(예: 비공개 드라이브 공유)는 대개 실패합니다. 공개 이미지 주소나 Cloudinary 업로드를 쓰세요.

Q로컬에서 테스트하고 싶습니다.

http://localhost:5173/callback처럼 localhost로 시작하는 주소만 http로 허용됩니다. 127.0.0.1이나 사설 IP는 등록되지 않으니, 로컬에서 시험할 때도 localhost를 쓰세요.

Q"invalid-code"가 나옵니다.

code를 두 번 교환했거나(새로고침 포함) 5분이 지났습니다. 콜백 주소에서 code 쿼리를 지우고 다시 로그인하세요. 교환 결과는 세션에 저장해 두고 재사용해야 합니다.

Q"지금은 LK 로그인을 쓸 수 없습니다"가 나옵니다.

Soft Hub의 로그인 API 표가 아직 준비되지 않은 상태입니다. 관리자가 supabase_schema.sql 12번 항목을 실행하면 바로 해결됩니다. 사용자는 이 화면에서 아무 정보도 전달하지 않았습니다.

Q모바일에서 화면이 가로로 넘칩니다.

긴 주소·코드가 원인인 경우가 많습니다. 말줄임(text-overflow: ellipsis)이나 word-break: break-all을 넣고, pre에는 overflow-x:auto를 줍니다. 390px 폭에서 한 번 확인하세요.

Q테마를 바꿔도 내 도구만 밝게 보입니다.

Soft Hub는 cream_theme 값(light/dark)을 씁니다. 내 페이지도 이 값을 읽어 색을 바꾸면 허브와 함께 전환됩니다.

QDrive API가 "not-connected"만 돌려줍니다.

사용자가 Soft Hub에서 Google Drive를 아직 연결하지 않은 상태입니다. auth.html#backup 또는 drive.html#cloud에서 연결하도록 안내하세요. 앱이 토큰을 직접 받아 오는 방식은 지원하지 않습니다(토큰 격리).

QDrive 브리지가 "denied"를 돌려줍니다.

세 가지 중 하나입니다. ① Client ID 오타 ② 앱에서 drive:app을 켜지 않음 ③ 지금 페이지의 출처가 등록된 Redirect URL의 출처와 다름. 특히 www 유무와 포트 번호를 확인하세요.

Q짧은 링크가 "rate-limited"로 실패합니다.

앱당 24시간 40개 한도입니다. 테스트 중이라면 하루를 기다리거나, 실제 사용자 흐름에서만 링크를 만들도록 바꾸세요. 같은 내용을 반복 생성하지 말고 한 번 만든 링크를 재사용하세요.

Q알림이 "grant-required" 또는 "blocked-by-user"로 실패합니다.

grant-required는 그 사용자가 이 앱에 push:send로 동의한 기록이 없거나, auth.html에서 권한을 해제한 경우입니다. blocked-by-user는 사용자가 push-center.html에서 이 앱 알림을 끈 경우입니다. 둘 다 정상적인 거부이니 재시도하지 말고 안내만 하세요.

Q테마를 읽었는데 항상 dark로 나옵니다.

Soft Hub의 기본 테마가 dark이기 때문입니다(cream_theme 값이 없으면 dark). 브리지가 막혀 시스템 설정으로 대체된 경우에는 fallback: true가 함께 옵니다. 이때는 prefers-color-scheme 기반으로 직접 처리하세요.

Q다른 사람에게 내 앱의 동의 화면이 안 열립니다.

공개 승인 전이기 때문입니다. 관리자에게 API 앱 관리 → 공개 승인을 요청하세요. 본인 계정으로는 "개발자 테스트 모드"로 바로 쓸 수 있습니다.

Q도구를 지웠는데 상세 페이지 링크가 남아 있습니다.

삭제된 도구의 상세 페이지는 "도구를 찾을 수 없습니다" 상태가 됩니다. 이미 공유된 링크를 회수할 수는 없으니, 같은 내용을 다시 올리려면 새 주소로 등록하세요.

06 — SECURITY

Soft Hub API 보안 체계 및 개발자 보안 수칙

API를 붙이는 일은 편의를 얻는 대신 사용자의 정보를 만질 수 있는 권한을 얻는 일입니다. Soft Hub는 그 권한을 작게 나누고, 만료시키고, 언제든 회수할 수 있게 설계했습니다. 이 장은 그 체계가 실제로 어떻게 동작하는지, 개발자가 무엇을 지켜야 하는지를 순서대로 설명합니다.

06-1. 무엇을 막으려는가 — 위협 모델

보안은 "무엇이 잘못될 수 있는가"를 먼저 정할 때 구체해집니다. Soft Hub가 상정하는 여섯 가지 위협과 대응입니다.

위협구체적인 상황대응
사칭 로그인 화면공격자가 Soft Hub와 똑같이 생긴 페이지에서 비밀번호를 받아 감로그인은 언제나 oauth.html 한 곳에서만. 앱은 로그인 화면을 복제할 수 없고, 동의 화면에 앱 이름과 돌아갈 host가 표시됨
Redirect 조작허용되지 않은 주소로 code를 보내 가로챔등록된 Redirect URL과 글자 단위 정확 일치일 때만 발급·이동. 불일치면 이동 없이 오류 화면
CSRF다른 사이트가 사용자를 몰래 로그인시켜 계정을 묶음매 요청마다 새 state를 만들고 콜백에서 비교. 불일치면 code 폐기
토큰 탈취외부 도메인이 사용자의 Google Drive 토큰을 받아 전체 Drive를 읽음토큰은 Soft Hub 출처의 iframe 안에만. 외부 앱은 postMessage로 자기 폴더만 읽고 씀
남용한 앱이 링크 수천 개를 만들거나 알림을 폭탄처럼 보냄서버 함수가 앱·사용자별 하루 한도를 세고, 본문 크기를 제한
권한 잔존한 번 동의한 앱이 계속 정보를 받거나 알림을 보냄oauth_grants 기록 + auth.html 원클릭 권한 해제 + 관리자 정지

06-2. 하이브리드 승인 정책 — 테스트와 공개를 나눈다

개발 편의를 위해 모든 앱을 처음부터 관리자 승인 대기로 두면 테스트가 막힙니다. 반대로 아무나 바로 공개하면 사칭 앱이 사용자에게 노출됩니다. 그래서 두 단계로 나눴습니다.

상태만든 본인다른 사용자전환 방법
공개 승인 대기 (is_approved = false)로그인·동의·API 모두 가능(테스트 모드 안내 표시)동의 화면이 열리지 않음관리자가 [공개 승인]
공개 승인 (is_approved = true)가능가능관리자가 언제든 [승인 해제]
정지 (is_active = false)불가불가관리자가 [정지] / [다시 켜기]
  • 서버 함수 oauth_issue_code가 이 규칙을 직접 검사합니다. 화면만 막고 서버는 열어 두는 식이 아닙니다.
  • 정지된 앱은 이미 발급된 code도 교환되지 않습니다(invalid-client).
  • 발견 탭 노출(community_apps)은 별도의 승인 절차를 그대로 씁니다. API 앱 승인과 도구 게시 승인은 서로 다른 심사입니다.
관리자 화면: admin.html → 접수된 신고(신고 확인·앱 중지) · API 앱 관리(공개 승인·정지 킬 스위치).

06-3. 토큰 격리 — Drive 토큰은 앱에 주지 않는다

가장 조심해야 하는 자원은 Google Drive 접근 토큰입니다. 이 토큰 하나면 사용자의 파일을 넓게 만질 수 있기 때문에, 외부 도메인에는 절대 전달하지 않습니다. 대신 같은 출처의 브리지 페이지가 대신 일합니다.

01
외부 도구 → 브리지 요청

도구는 숨은 iframe으로 drive-bridge.html을 띄우고 postMessage로 "settings를 저장해 달라"고 요청합니다. 토큰은 보내지 않습니다.

02
브리지의 3단 검증

① Client ID가 등록된 앱인가 ② drive:app을 허용했는가 ③ 부모 창의 출처가 등록된 Redirect URL의 출처와 같은가. 하나라도 어긋나면 응답하지 않습니다.

03
폴더 고정

브리지는 언제나 SoftHub_Apps/{client_id} 안에서만 읽고 씁니다. 키는 영문·숫자·-·_ 64자로 제한해 ../ 같은 경로 조작을 막습니다.

04
응답만 돌려준다

외부 도구가 받는 것은 요청한 값(JSON)뿐입니다. 토큰·파일 ID 목록·다른 폴더는 전달되지 않습니다.

앱이 Redirect URL의 출처와 다른 도메인에서 브리지를 띄우면 거부됩니다. 예를 들어 https://studio-pine.example로 등록한 앱은 https://other.example에서 Drive를 쓸 수 없습니다. 도메인을 옮겼다면 API 대시보드에서 Redirect URL도 함께 바꾸세요.

06-4. 최소 권한 — 필요한 스코프만 켠다

동의 화면에는 앱이 요청한 스코프가 하나씩 이름과 설명으로 나옵니다. 사용자가 "무엇을 넘기는지" 모르는 채 동의하는 일을 줄이기 위해서입니다. 개발자는 반대로 쓰지 않는 스코프를 꺼야 합니다.

  • 나중에 스코프를 늘리면 사용자는 다음 로그인에서 늘어난 항목을 다시 보게 됩니다. 조용히 늘어나지 않습니다.
  • 스코프를 줄이면 그 기능은 즉시 막힙니다(scope-required).

06-5. state 검증과 Redirect URI 화이트리스트

로그인 흐름에서 개발자가 직접 책임지는 두 가지입니다. 이 둘만 지켜도 가장 흔한 사고를 막습니다.

state — 매번 새로 만들고, 돌아오면 비교한다

state 생성 · 저장 · 비교 
/* 1) 로그인 시작 — 매번 새 값 */
function startLogin() {
  var abc = 'abcdefghijkmnpqrstuvwxyz23456789';
  var out = '', arr = new Uint8Array(20);
  crypto.getRandomValues(arr);
  for (var i = 0; i < arr.length; i++) out += abc[arr[i] % abc.length];

  sessionStorage.setItem('lk_state', out);      // 이 탭에만 저장
  location.href = 'https://helpaboutflux-cpu.github.io/cream-ai-hub-android/oauth.html'
    + '?client_id=' + encodeURIComponent(CLIENT_ID)
    + '&redirect_uri=' + encodeURIComponent(REDIRECT_URI)
    + '&response_type=code&scope=' + encodeURIComponent('profile:basic')
    + '&state=' + encodeURIComponent(out);
}

  • 새로고침으로 같은 code를 다시 보내면 실패합니다. 교환 결과를 세션에 저장하세요.

06-7. 사용자 연결 관리와 권한 철회(Revoke)

동의는 한 번으로 끝나지 않습니다. Soft Hub는 사용자가 준 권한을 oauth_grants에 남기고, 언제든 되돌릴 수 있게 합니다.

  1. 기록 — 동의할 때마다 (user_id, client_id, scopes, granted_at)이 저장되고, code를 발급할 때마다 last_used_at이 갱신됩니다.
  2. 확인 — 사용자는 auth.html → 연결된 앱에서 자기가 허용한 앱, 권한 범위, 연결 날짜를 봅니다.
  3. 해제 — [권한 해제]를 누르면 revoked_at이 기록됩니다. 이후 push:send는 서버에서 grant-required로 거부됩니다.
  4. 재동의 — 다시 쓰려면 앱에서 로그인 버튼을 눌러 oauth.html에서 새로 동의해야 합니다.
개발자 관점: 사용자가 권한을 해제했을 수 있으니 알림·Drive 호출 실패를 정상적인 상태로 처리하고, "다시 로그인해 주세요" 안내를 준비하세요.

06-8. 의심 서비스 신고와 차단 절차

사용자가 언제든 멈출 수 있어야 합니다. oauth.html의 오른쪽 아래에는 이 서비스 신고 버튼이 항상 떠 있습니다. 로그인 전 화면, 동의 화면, 오류 화면 어디서나 쓸 수 있고, 누르면 팝업이 아니라 그 자리에 작은 패널이 펼쳐집니다.

단계누가무엇을어디서
1사용자사유(피싱·사칭 / 과다 요구 / 악성 링크 / 기타)와 메모를 남김oauth.html 우측 하단 · tool.html '이 도구 신고'
2시스템요청된 Client ID·Redirect URL과 함께 oauth_reports에 기록서버 표(관리자만 읽기)
3관리자신고 목록에서 대상 앱·도구 확인, 필요하면 즉시 조치admin.html → 접수된 신고
4관리자[앱 사용 중지] → is_active = false (모든 API 즉시 차단)신고 목록 · API 앱 관리
5관리자도구 신고면 [도구 반려] → 발견 탭에서 내림신고 목록
  • 신고에는 Client ID와 Redirect URL이 함께 담겨 관리자가 어느 앱인지 바로 찾을 수 있습니다.
  • 사용자에게는 "신고했습니다. Soft Hub 관리자가 확인합니다"라는 인라인 안내만 보입니다. 신고자 정보는 앱에 전달되지 않습니다.
  • 앱이 사칭으로 정지되면 oauth.html은 "사용이 중지된 서비스입니다"를 보여 주고 어떤 정보도 넘기지 않습니다.

06-9. 개발자 보안 수칙 (지켜야 할 것)

  • 비밀번호를 직접 받지 않는다. 로그인은 언제나 oauth.html로 보낸다.
  • 받은 정보는 필요한 만큼만, 필요한 동안만 보관한다. sub가 이메일보다 안전하다.
  • 닉네임·본문을 화면에 넣을 때 textContent를 쓴다. innerHTML은 금지.
  • 서버가 준 nickname을 파일 이름·경로·DB 키로 쓰지 않는다.
  • 스코프는 기능이 실제로 동작할 때만 켠다. "나중에 쓸 것 같아서"는 이유가 되지 않는다.
  • 토큰·code·state를 URL 로그·분석 도구·광고 스크립트로 흘리지 않는다.
  • 콜백 URL에서 code를 한 번만 쓰고, 결과를 저장해 재사용한다.
  • 앱이 정지·미승인일 때를 정상 상태로 처리한다(빈 화면·무한 로딩 금지).
  • 사용자 데이터를 다른 도메인·제3자에게 넘기지 않는다.
  • 정기적으로 API 대시보드에서 Client ID를 재발급하고, 쓰지 않는 앱은 삭제한다.

06-10. 사고가 났을 때 — 대응 순서

  1. 즉시 멈춘다 — API 대시보드에서 해당 앱을 정지하거나 Client ID를 재발급합니다. 정지는 로그인·Drive·공유·알림을 모두 끊습니다.
  2. 범위를 확인한다 — 어떤 스코프가 켜져 있었는지, 기간은 얼마인지 확인합니다. Drive는 앱 폴더 밖으로 나갈 수 없고, 프로필은 이메일을 포함하지 않습니다.
  3. 사용자에게 알린다 — 앱 화면에 공지하고, 사용자가 auth.html에서 권한을 해제할 수 있다는 점을 안내합니다.
  4. 재발 방지 — state 검증 누락, Redirect URL 오타, 스코프 과다 허용 중 무엇이 원인이었는지 확인하고 코드를 고친 뒤 다시 공개 승인을 요청합니다.
Soft Hub가 대신 지켜 주는 것: Redirect 정확 일치, code 5분·1회용, Drive 폴더 격리, 사용자별 한도, 권한 철회. 개발자가 지켜야 할 것: state, 최소 권한, 안전한 출력, 비밀번호 미수집.

도구 등록

  • 도구 주소가 새 탭에서 실제로 열린다.
  • 이름이 60자 이내이고, 무엇을 하는 도구인지 이름만 봐도 짐작된다.
  • 한 줄 소개의 첫 40자 안에 핵심 기능이 들어 있다.
  • 분류가 사용자 관점에서 맞다.
  • 아이콘과 브랜드 컬러가 도구의 성격과 어울린다.
  • 스크린샷 주소가 공개 상태이고, 첫 장이 첫 화면이다.
  • 390px 폭에서 가로 스크롤이 없다.
  • 라이트·다크 양쪽에서 글자가 읽힌다.
  • 이모지와 팝업이 없다.

확장 API (Drive · 공유 · 알림 · 테마)

  • 실제로 쓰는 스코프만 켰다(최소 권한).
  • Drive 키가 [A-Za-z0-9_-] 64자 이내이고, 256KB를 넘지 않는다.
  • Drive not-connected·denied 상태를 사용자에게 안내한다.
  • 공유 링크는 한 번 만들고 재사용한다(하루 40개 한도).
  • 공유 본문에 개인정보를 넣지 않는다.
  • 알림은 동의한 사용자에게만, 하루 10건 안에서 보낸다.
  • 알림 grant-required·blocked-by-user를 정상 상태로 처리한다.
  • 테마 값이 없을 때(fallback)를 대비한 기본 색이 있다.

보안

  • Redirect URL을 등록값과 글자 하나까지 같게 썼다.
  • state를 매번 새로 만들고 콜백에서 비교한다.
  • code를 한 번만 교환하고 결과를 저장한다.
  • 닉네임·본문을 textContent로만 넣는다.
  • 비밀번호를 직접 받지 않고, 받은 값을 로그·분석 도구로 보내지 않는다.
  • 문제가 생겼을 때 앱을 정지할 수 있는 절차를 알고 있다(06-10).

LK 로그인 연동

  • API 대시보드에 앱을 만들고 Client ID를 받았다.
  • Redirect URL을 코드에 쓴 값과 글자 하나까지 같게 등록했다.
  • 로그인 버튼이 매번 새 state를 만들고 저장한다.
  • 콜백에서 state를 비교하고, 다르면 code를 쓰지 않는다.
  • error=access_denied를 사용자 취소로 처리한다.
  • 교환 결과를 저장해 새로고침 때 재사용한다(같은 code 재사용 금지).
  • 닉네임을 textContent로 넣는다(innerHTML 금지).
  • 비밀번호·이메일을 요구하지 않는다.
